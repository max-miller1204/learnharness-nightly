## Revision, 2026-11-20: copy T3's update flow exactly

The owner's ask: "copy to a T literally exactly what T3 does for their update flow... literally everything the same... copy the source code if you have to." Updating felt clunky, and hovering the update control no longer showed what the update is. The research behind this revision maps both flows with file and line.

### Decisions (owner, 2026-11-20)

- **Copy T3's flow:** its states, icons, hover text, release-notes popover (header "Update ready to download", the line "X · 3h ago", T3's link labels), retry tooltips, confirm text and menu dialogs.
- **Toasts like T3's** (reverses the 2026-11-17 "no toast" decision).
- **Update everything like T3's:** its in-app dialog with the machine table, and the sidebar progress capsule ("N of M updated", "Restart in 5s" with Later, Retry, Dismiss). It is also offered when only the server is behind this app.
- **The server offers, then downloads on a click,** like T3: a check that finds a newer version shows "available" with a Download button (reverses the background download).
- **No "Check for updates automatically" toggle** (T3 has none). Both the app and the server check 15 s after launch, then every 4 hours.
- **Desktop install** calls `quitAndInstall` silent with force-run-after, like T3.
- **The launcher's commit and rollback stay** for server updates: a hidden safety net. The user sees T3's flow.
- **In a plain browser the control stays visible:** there the self-hosted server is the app (T3 hides it unless servers need updating, `SidebarUpdatePill.tsx:412`).

## Changes

### 1. Shared shapes

- `ReleaseNoteGroup = { version: string; releasedAt?: string; items: string[] }`. `items` are plain sentences; an item shaped `**Label.** detail` renders the label bold (T3's convention). At most 8 items per group, each at most 220 characters (T3's limits).
- `UpdateState` (desktop and web) gains `"available"` in `status` (found, not downloaded), `releaseNotes: ReleaseNoteGroup[]` (newest first, versions newer than the running one up to the offered one, at most 6 groups) and `omittedReleaseCount: number` (groups beyond 6). Both default to empty. The self-hosted state also carries `instance`, an id of the server process: a restarted server counts revisions from 0 again, so a client that sees a new `instance` resets its revision guard instead of ignoring the new server (prove round 1 finding).

### 2. Notes at release time (nightly.yml, `scripts/generate-release-notes.ts`)

- New script, run with plain `node` (erasable TypeScript, built-ins plus `gh`, no new dependencies). Inputs: `--repository --tag --ref --previous-tag --version --output`. It reads `git log --no-merges previous..ref` (everything on main, including imported upstream changes), and the bodies of the PRs those subjects name (`gh api graphql`, trimmed to 300 characters as T3 does), and asks OpenRouter (`https://openrouter.ai/api/v1/chat/completions`, model `OPENROUTER_MODEL` or `anthropic/claude-haiku-5.5`, JSON output, reasoning effort low, 3 minute timeout).
- Prompt: T3's `SUMMARY_INSTRUCTIONS` adapted to LearnHarness (web app, desktop and self-hosted server; up to 7 user-facing highlights; skip internal work, docs, tests, CI and dependency bumps; group commits with the same outcome; zero is allowed; short label plus one sentence of at most 20 words; no headings, PR numbers, hype or em dashes). The model returns `{ highlights: [{ label, detail, commits }] }`; commit numbers must point at real input commits or the whole result is rejected (T3's check). A number may come back as a string, `"8"` or `"[8]"`, and reads as that commit (prove round 2 finding, user decision 2026-11-18).
- Items: one `**Label.** detail` per highlight (then the intro or footer once more, for older clients). If fix/perf commits were left out, their count is the `footer` ("Plus 3 more bug fixes.", T3's wording and pluralisation), or the `intro` ("3 bug fixes.") when there are no highlights. No highlights and no fixes: no items. `stats` is T3's release header without the version, "12 changes from 2 contributors": every commit of the range, and the contributors as T3's `countContributors` counts them (PR authors without bots, plus direct pushers). A commit's "(#N)" uses this repo's PR #N only when that PR merged the commit or shares its author: an imported upstream commit keeps upstream's number, so it counts by its git author and gives the model no body. A GraphQL query naming a missing PR still yields the others (gh's stdout on a non-zero exit).
- It writes `notes.json` (`{ version, publishedAt, items, stats, footer? | intro? }`) and nothing on failure. The workflow step runs with `continue-on-error: true` and `OPENROUTER_API_KEY` from secrets.
- Fallback (next step, when `notes.json` is missing): items are the commit subjects of the range, newest first, with a trailing ` (#N)` removed, first 8, and `stats` counts the git authors (no PR authors there).
- Release body (`notes.md`): T3's generated summary (`summaryBody`: "**vX** · stats", the intro, the items as bullets, "### <footer>"; omitted when there is nothing), then a folded `<details><summary>Full changelog</summary>` holding today's commit list, then today's build and install lines. The desktop parser below cuts at `<details>`, as T3's does.
- `latest.json` gains `notes: [{ version, publishedAt, items, stats?, intro?, footer? }]`, newest first: this release's entry, then the entries from the previous `latest.json` on the `nightly` release, deduped by version, newest 30 kept (the same 30 the prune keeps, so every listed version still has a live release page). `make-feed.ts` gets `--notes <notes.json>` and `--previous <latest.json>`.
- `parseFeed` accepts the field and drops malformed entries instead of failing; old launchers and servers ignore it. The `feed-check.yml` repair copies a release's `latest.json` as today, notes included.

### 3. Self-hosted server updater (`src/server/self-update.ts`)

- Checks 15 s after start and every 4 hours (`CHECK_INTERVAL_MS`); Check for updates works any time. No toggle (revision PR 5).
- A check that finds a newer version offers it ("available", with its notes); it downloads only on a click (revision PR 5).
- No automatic apply: the idle loop (`IDLE_POLL_MS`, `scheduleIdleApply`) is removed. Applying happens only through `install()` (the Install button, POST `/api/updates/install`, `lh update --now`).
- Checks keep running while a version is ready, and the ready one stays offered. `install()` first re-checks the feed (T3's "a download can be hours old" rule), installs the newer version if one appears and stages, and otherwise installs the ready one; a failed re-check installs the ready one.
- Notes: on each successful check the state's `releaseNotes` and `omittedReleaseCount` come from the feed's `notes`, filtered to versions newer than the running one and not newer than the feed's version. Each check also merges the feed's notes into the notes cache (section 6).
- Notices: the "updated" notice and `UPDATED_NOTICE_MS` go (What's new replaces them). The rolled-back notice stays and is now dismissible per server: POST `/api/updates/notice/dismiss` records its id (`rolled-back:<version>:<at>`) in the updates record (section 6); a dismissed notice is not adopted again at boot, and dismissing clears its text from the Settings row too.
- `appIsIdle()` and `/api/health`'s `idle` stay (the launcher's own protocol hand-off and `lh status` use them).
- New `runningWork()` (the same sources as `appIsIdle`) and GET `/api/updates/running` → `{ items: [{ kind, title }] }` with kind `turn`, `compaction`, `job`, `plugin-worker` or `extraction`, and the chat, job, worker or extraction title.
- `lh update` (no `--now`) text: "It installs when you click Install in the app, or run `lh update --now`."

### 4. Desktop updater (`electron/main.cjs`, `electron/preload.cjs`)

- `autoDownload = false`, `autoInstallOnAppQuit = false`, `fullChangelog = true`.
- Automatic checks: 15 s after launch, then every 4 hours. Manual checks unchanged.
- `update-available` sets `available` with the version and notes (no download). New IPC `lh:update:download` (preload `downloadUpdate()`) calls `downloadUpdate()`; progress shows `downloading`; done shows `downloaded`.
- Install (`lh:update-install`, trusted windows only): first re-checks; when the feed offers a version newer than the downloaded one, downloads it, then installs that one; otherwise installs the downloaded one. A failed re-check (feed unreachable) installs the downloaded one. If downloading the newer one fails, nothing installs and the server keeps running: electron-updater 6.8.9 has already deleted the old download, so the state returns to `available` for the newer version and the user can retry (decided after review, 2026-11-17). Before quitting it saves the installed version's notes to the notes cache (section 6) and kills the server first, as today. It calls `quitAndInstall(true, true)` (silent, run after; revision PR 3). If the app has not started quitting 10 s after `quitAndInstall` (a cancelled admin prompt, a missing installer), it relaunches on the current version so it is never left without its server.
- Notes: `electron/release-notes.cjs`, a port of T3's `apps/desktop/src/updates/releaseNotes.ts` (HTML/markdown stripping, `<details>` cut, 6 groups, 8 items, 220 characters), turns electron-updater's `releaseNotes` (string or per-version array) into `ReleaseNoteGroup[]`, without T3's channel filter. It reads a generated summary's stats, intro, items and footer, and a plain list's newest 8 with its whole count (revision PR 2).
- The rule "a later check must not hide a staged update" stays.

### 6. What's new popup

- Data, in the data folder (`config.ts` data root, so "per server": every browser on that server sees the same thing):
  - `release-notes.json`: the notes cache, `{ groups: ReleaseNoteGroup[] }`, newest 30 versions. Written by the self-hosted updater on each check and by Electron main before installing.
  - `updates.json`: `{ lastSeenVersion?: string; dismissedNotice?: string }`, written atomically.
- GET `/api/whats-new` → `{ version, releaseNotes, omittedReleaseCount } | null` (`releaseNotes` as in `UpdateState`). Null when the running version is not an exact version (dev builds), or equals `lastSeenVersion`. With no `lastSeenVersion` (fresh install, or the first build with this feature) it records the running version and returns null, so nobody gets a popup for an install. Groups: cached groups with `lastSeen < version <= running`, newest first, at most 6, same limits.
- POST `/api/whats-new/seen` `{ version }` records it and emits `whats-new-changed`; every open client refetches, so seeing it on one device closes it on the others.
- Popup (`components/whats-new-dialog.tsx`, HostDialog, mounted once in the app shell, inside the dialog providers it needs): title "What's new in X"; the same sections as the pill popover (shared renderer); with no groups the body is "Updated to version X." and a "View release on GitHub" link to that release. One button "Got it". Any dismissal (button, Esc, backdrop) marks it seen.
