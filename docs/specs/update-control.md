# Spec: update fixes and the sidebar update control

Status: decided by the owner, 2026-11-18; revised 2026-11-20 to copy T3 exactly (the decisions and PR split are in [t3-style-updates.md](t3-style-updates.md), "Revision, 2026-11-20"). Base: main at bf262b7.
T3 Code reference: github.com/pingdotgg/t3code at 7e4c429 (MIT), `SidebarUpdateControl` in `apps/web/src/components/sidebar/SidebarUpdatePill.tsx`, `DesktopUpdateStatusIcon.tsx`, `desktopUpdate.logic.ts`.

## Bugs fixed

1. **Automatic checks never ran after an update.** A server started by an update runs as the launcher's trial, which skips the startup check, so the next automatic check was 4 hours away. Now the server checks 15 s after the launcher commits it. Not at once: the launcher deletes leftover `*.tmp` version folders right after a commit, which would delete a download being unpacked (found in the prove run); T3 also checks 15 s after launch. The interval stays 4 hours, like T3 (owner decision). The GitHub "Pre-release" flag is not involved: automatic and manual checks read the same `nightly/latest.json`, never `releases/latest`.
2. **The update icon stayed after Install until a reload.** Behind Tailscale Serve, the reconnect during the restart gets a 502, and EventSource then closes for good, so the page never heard anything again. The events channel now opens a new EventSource when one closes: after 1 s, doubling per failed try up to 5 min (T3's connection supervisor), never while the tab is hidden, and at once when it shows again. The open refetches as any reconnect does.
3. **The "Settings (⌘,)" hint stayed up after closing Settings.** The dialog hands focus back to the Settings button, and the tooltip opened on any focus. Tooltips now open on focus only when it is `:focus-visible` (keyboard), as the update pill already did.

## The sidebar update control

One round button (`size-8 rounded-full`, 16 px glyph) at the right end of the sidebar's Settings row, on the web and desktop apps (T3 hides it in the browser; here updates are server side). `resolveUpdateControl` picks the state, in T3's order:

| State | Icon | Tooltip | Click |
|---|---|---|---|
| reload (server version differs from the page's) | RotateCw with check badge | server newer: "Updated to X. Click to reload." (shown only until the page reloads by itself, see Reload below); server older (after a rollback): "Server is on X. Click to reload." | reload, confirming first when any editable text field on the page has unsent text: "You have an unsent message. Reload anyway?" (Cancel / Reload) |
| checking | RefreshCw, spinning, disabled | "Checking for updates…" | nothing |
| downloading | download arrow in a progress ring that fills with the download (see Download progress below), disabled | "Downloading update (NN%)", or "Downloading update" while the size is unknown; "Preparing update" with a full ring while the server checks and unpacks it | nothing |
| downloaded | RotateCw with check badge | "Update X downloaded. Click to restart and install." | the install confirm dialog |
| restarting (Install and restart confirmed, see Restarting below) | RotateCw with check badge, the arrow spinning, at 60% opacity, disabled | "Restarting to install X…" | nothing |
| available (the desktop app's; the server's too from revision PR 5) | download arrow with a dot | "Update X ready to download" | download |
| rolled-back notice | warning triangle | the notice text | dismiss |
| disabled | RefreshCw at 60% opacity, `aria-disabled` | "Updates unavailable" / "Automatic updates are not available in this build." | nothing |
| idle, up to date, check failed | RefreshCw | "Check for updates" | the same check as Settings > Check for updates |

The release notes popover follows T3's rule (`SidebarUpdatePill.tsx:58-63, 95, 279-280` at df09ced7): it opens on hover, or on keyboard focus, whenever the state is about an offered update (download, downloading, install, restarting, everything, app-download, app-install) and that update has notes, and never while an Update everything run is going. The notes are this app's own (from `window.lh.desktopUpdate`'s `status()`) for everything, app-download, app-install and this app's download, and the server's otherwise. With no notes the plain tooltip shows. Keyboard: see t3-style-updates.md, revision PR 1.

Spin: a click latches the spin and remounts the icon so it starts from zero; it turns at least once and keeps turning while the state is `checking`, then stops at the next turn boundary. `motion-safe` only; paused while the tab is hidden (an inline `animation-play-state`, so the class's `animation` shorthand can't undo it).

Download progress (owner decision, 2026-11-19, "copy T3"; replaces the plain arrow with no ring): while an update downloads, the control shows T3's ring (`DesktopUpdateStatusIcon.tsx:15-18, 56-90` at 3ce21458): a 32 x 32 SVG circle of radius 14 around the 16 px download arrow, starting at the top, its track at 22% opacity, filled by `stroke-dashoffset` with a 300 ms ease-out transition (none under reduced motion). The tooltip and label are T3's (`desktopUpdate.logic.ts:134-139`): "Downloading update (NN%)" with the percent rounded down, or plain "Downloading update" and an empty ring while the size is unknown. It covers both downloads that show this state:

- The desktop app's own update: electron-updater's `download-progress` percent goes into the app's update state as `downloadPercent` (the local window gets it pushed; the window onto a self-hosted server reads it from `window.lh.desktopUpdate` status every 5 s, as before). It starts at 0 when the download starts, as T3's does: from Download, from Update everything's pinned download and from its app-only Try Again.
- The server's own download (`src/server/self-update.ts`): the bytes are counted as they arrive against the response's Content-Length, and the percent is in GET /api/updates (and health) as `downloadPercent`, null until the size is known and when there is none (no Content-Length, or a compressed transfer). Once every byte is in, the server checks the SHA-256 and unpacks the archive before the version is ready (owner decision, 2026-11-19; T3 has no such step): the status stays "downloading", so Install still waits for "downloaded", but `preparing` is true and `downloadPercent` is 100, so the ring is full and the label reads "Preparing update" (Settings: "Preparing version X…").

Both pass a new percent on only at each whole 10% and at 100%, T3's `shouldBroadcastDownloadProgress` (`apps/desktop/src/updates/DesktopUpdates.ts:325-341`), so a download sends about ten update events, not one per chunk. `downloadPercent` is null in every other state. When this app and the server both download, the ring shows this app's, the one the control is showing.

Restarting (owner decision, 2026-11-19): after "Install and restart" nothing showed until the restart and the button stayed clickable, so people pressed it again. Now, from the confirm until the restart, the button greys out (60% opacity) and can't be clicked, the RotateCw arrow spins (the check badge stays put; `motion-safe` and paused while the tab is hidden, like the check spin), and the label reads "Restarting to install X…" with the version. Like T3's `isActionPending` (`SidebarUpdatePill.tsx:278` at 3ce21458), it is a flag in the page, set on the confirm: the local desktop app's own update (main re-checks, then quits and installs) and the server's self-update (POST /api/updates/install, then the launcher's restart) both keep the state "downloaded" until the restart, so the flag holds until the page reloads or the app quits. If the restart or install fails, the state moves on and the control is the normal button again, with the existing error behavior: the server's error state (the check button), the app offering a newer version it couldn't download (Download), a rollback notice, or a failed POST (Install again). The app answers whether it took the install, and turns it down while an Update everything run owns its updater; the local app's Restarting shows only after its yes (until then the normal button, focus untouched), so a no keeps Install without a flash of Restarting. A check spin started elsewhere outranks it for a moment without ending it. The button stays the same element through every state change (the release notes popover anchors on the tooltip's trigger), so keyboard focus stays on it; after the confirm the pill puts focus back on it itself, since the dialog only returns focus to an enabled opener. In the desktop app's window onto a server, the app's run (`phase` "updating") shows this state once the server runs exactly this app's version and its launcher committed it (`committed`, the run's own condition in `electron/update-everything.cjs`), since only this app's restart is left: the app-install confirmation's restart, and the last step of Update everything; while the server is behind or still an uncommitted trial it stays "everything". Settings' own Install button is unchanged.

Reload: GET /api/updates carries `runningVersion`; the page compares it with its own build version and offers a reload whenever they differ (owner decision).

Automatic reload (owner decision, 2026-11-18, replaces "it never reloads on its own"): once the server is back and runs a newer version than the page's code, every open page reloads by itself: the window where "Install and restart" was clicked and every other tab or window, in a browser or a desktop app window on a remote server (the local desktop app restarts as a whole). Unsent text does not stop it and there is no confirm. It happens at most once per server version per tab: the tab remembers every version it reloaded for (the last 50) in sessionStorage, so a page whose code still doesn't match after the reload (a stale cache) keeps the button instead of looping, also when the server goes back and forth between versions (found by the proof: remembering only the last version let a stale tab reload for .73, .74, then .73 again); without usable sessionStorage the page never reloads by itself and keeps the button. After a rollback (server older than the page) the page does not reload by itself; the button waits for a click. The button's click stays as the fallback, with its unsent text confirm. "Back" means the trial server answers: an update first runs as the launcher's trial, so a page can reload onto a trial that then fails its health check and rolls back; that page then shows "Server is on X. Click to reload." (no loop).

Unsent text: any non-empty, user-editable text field (PathInput boxes, textareas such as the side-question box and the comment editor, text inputs), skipping read-only, disabled and hidden fields and search, find or filter boxes.

GET /api/health stays public (the launcher calls it without a credential) and keeps `runningVersion` and the update state, but update error text (`message` while `status` is "error", the reason in a rollback notice) only goes to a signed-in or paired caller; others still see `status: "error"` and a generic rollback notice (owner decision). `lh status` asks with its CLI session, so it still shows the details. Health's `idle` is false whenever an update check or download is in flight, whatever the state shows (a ready version stays "downloaded" while a newer one is fetched; found by the independent proof), so a launcher relaunch (which waits for idle) can't stop the server mid-download. The other work that blocks idle is unchanged: chat turns, compactions, background jobs, plugin workers and extractions.

What's new waits for the reload (owner decision): while the server runs a newer version than the page's code, the "What's new" popup is held back (not shown, not marked seen), so the reload button stays visible until the page reloads by itself. It shows once on the first page that runs the new version, after the automatic reload (or a click on the button, or the next time the app opens). GET /api/whats-new already answers the running version, so the page compares that with its own build version.

## Update everything (roadmap item 23 PR 2)

Only in the desktop app's window onto a self-hosted server, which gets `window.lh.desktopUpdate` (see [desktop-server-list.md](desktop-server-list.md), PR 2). `resolveUpdateControl` takes this app's status too, in T3's order (`SidebarUpdatePill.tsx:82-117` at 8cf97b5): after reload and checking, this app's downloading, then:

| State | Icon | Tooltip | Click |
|---|---|---|---|
| everything (this app has a newer version and the server is behind it, or a run is going and the server is behind or an uncommitted trial; also when only the server is behind this app) | CircleArrowUp (T3's `DesktopUpdateStatusIcon.tsx:119`) | "Update this app and 1 server" (T3's `updateEverything.logic.ts:765-772`), with this app's release notes; with only the server behind, "Update 1 server" (T3's sentence for servers alone, `:811-822`) and no notes, since this app offers none | T3's in-app Update everything dialog (revision PR 7); disabled while a run is going |
| app-download (the server already runs that version) | download arrow with a dot | "Update X ready to download" | download this app's update |
| app-install (downloaded, the server already runs it) | RotateCw with check badge | "Update X downloaded. Click to restart and install." | the same Update everything confirmation, which then only restarts the app |
| restarting (a run is going and the server runs exactly this app's version, committed) | as restarting above | "Restarting to install X…" | nothing |

T3 shows "everything" only while a server is behind (`useUpdateEverything.ts:104`), so the plain app states cover the rest. Its target is `localUpdateVersion ?? APP_VERSION` (`:57`), so a server behind this app is offered the run with no app update, and the run installs nothing locally (`SidebarUpdatePill.tsx:373-386`). `serverBehindApp` is that rule: this app has no active offer, plans the flow (`serverOnly` in its status) and its updater is on, the server's version is older than this app's on the same release track (never across channels, `versionSkew.ts:62-70`), the server can update itself and shows no rollback notice (read first); a server's own download in progress keeps its progress ring. The dialog then lists the server alone, the run asks it for exactly this app's version through `install-version`, and the result toast reads "Updated 1 server". The check button checks the server and this app. The page reads this app's status every 5 s (the bridge has no push channel) and when the tab shows again. A page that sees its server back on a newer version reloads by itself as above, also during a run: it does so under the app's ghost cover, where the app's own rechecks wait until the run ends.

Settings → General there has two rows, with T3's labels (`UpdateEverythingDialog.tsx:91-92`): **Server X** (the existing row) and **This app Y**, T3's About button (`SettingsPanels.tsx:308-328`): Check for Updates, Checking…, Downloading…, Up to Date, Download, Install. The description reads "Update available." or "Current version of the application.", or why updates are off. Install installs only this app, like T3's (owner, 2026-11-20, revision PR 5; Update everything stays in the sidebar). Browsers and the local desktop window keep one "Version X" row.
