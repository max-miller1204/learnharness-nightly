## PR 1 · Connect, switch, and sign in

- First run offers **This computer** or **My server** (see the setup screen follow-up below). An explicit development launch with `LH_DEV_URL` continues to target its development server. **Switch server…** in the native app menu opens the app-owned server window with **This computer** and saved servers. One server is active at a time. The first successful setup sets the launch default. Later switches are temporary until **Set as default** is chosen. Each saved server has **Remove…**, which asks first, like T3's **Remove from this device…**, then forgets its pairing and credential. Removing the open server closes its window. Removing the default while other saved servers remain leaves no launch default until **Set as default**. Once every saved server and the default are gone, the setup screen shows again, also while This computer is open, and works like first setup: what is picked there (**This computer** or a newly paired server) becomes the launch default. Launch and Dock reopen never pick it. After a confirmed removal, focus moves to **Add a server**, or to **This computer** on the setup screen when the last server went. **Remove…** is refused, with the reason, for the server Update everything is updating. While a server is being removed or updated, nothing reconnects, rechecks or sends its credential for it. Server data stays on its own server.
- **Add a server** accepts a full LearnHarness pairing link and fills the HTTPS origin and 12-character code. Both fields can be entered manually. Submit explicitly to pair. A Tailscale hostname is a valid HTTPS address. Discovery, peer probing, the Tailscale CLI, and SSH are outside scope.
- Before pairing or reconnecting, Electron main reads the public server descriptor and requires an exact match with the desktop's client protocol. It exchanges a pairing code for a revocable bearer using `POST /oauth/token`. Before loading any remote UI it calls `GET /api/auth/session` with that server's bearer and without cookies. Authentication failure offers **Pair again** in the shell. Unreachable servers offer **Retry**, preserving the credential and launch default. **Switch server…** also checks the open server, so one that went away shows that it can't be reached, with **Retry**. **Switch server…** stays available. All desktop pairing happens in the app-owned window. A damaged saved list is ignored while **This computer** remains usable. **Reset saved servers** moves the damaged entry out of the active path without following symlinks or removing directory contents.
- Electron main owns persisted credentials, protected by OS-backed storage. The bearer is injected only into requests from the controlled top-level window to the exact selected HTTPS origin. The window uses its own session, context isolation and sandbox, with Node integration disabled. Redirects cannot carry the bearer off-origin. Switching closes the previous UI and streams, and remote mode leaves the bundled server off.
- LearnHarness loads the remote server's own server-rendered Next.js UI. For example, `app/page.tsx` reads the settings record on that server. T3 ships its UI in the desktop app at `t3code://app`. Remote windows have browser privileges and no local capabilities except two narrow bridges: Update everything's `window.lh.desktopUpdate` (PR 2) and the ChatGPT sign-in bridge `window.lh.chatgptSignIn`. Neither reaches the filesystem, local providers or another origin. External links and provider sign-in pages open in the system browser. Main redeems one-use sign-in actions at the selected origin and hands off only the provider destination. Ordinary HTTP errors stay in the remote window. Remote paths refer to the server. Item 24 adds file and folder byte uploads through the server UI and its capabilities.
- ChatGPT sign-in lives in the server's Settings, in its ChatGPT connection, and the Switch server list is only for servers (owner decision, November 20, 2026). In the desktop app the same Settings **Connect** stays one click: it calls `window.lh.chatgptSignIn`, one call whose only argument is an optional saved-account id the server issued, and which resolves `{ ok: true }` or a fixed error message. Main answers it only for the current remote window's main frame at its selected origin, and not while that server is being removed or updated. A new start ends the previous one after its cancel reaches the server. Main then reserves an ephemeral `127.0.0.1:0` listener before calling the existing `POST /api/subscriptions` ChatGPT `login` operation with its optional `desktopRedirectPort` field. Main resolves the existing one-use browser action without following its redirect, then validates the exact ChatGPT authorization endpoint and reserved callback URL before opening the system browser. A bind failure or callback mismatch stops before the browser opens. Main forwards the exact verified callback once through the existing `complete` operation to the original selected HTTPS origin with its bearer, that origin in `Origin`, and `x-learnharness-subscriptions: 1`. The server owns state, PKCE, token exchange and credentials. If the desktop abandons an acknowledged attempt, it asks the original server to cancel through the existing login controls. Web and phone retain paste-back.

## Follow-up · Quiet launch with the ghost dashboard

The owner approved this on November 18, 2026, after PR 1 showed the server list with **Connecting…** on every launch.

- With a saved default, launch opens the app window at full size straight away. It shows a ghost dashboard: a pulsing outline of the app layout (sidebar rows, search bar, session bars and footer rows, the empty main area, the composer and its controls row). It uses the Default theme colors, or the app's original light default (`#f5f5f3` page) when the theme is light. One quiet status line sits where the composer's text goes: **Connecting to max-desktop…** with the first label of the saved server's hostname, or the whole address for an IP literal, and **Starting LearnHarness…** for This computer. There's no pulse when the OS asks for reduced motion. macOS Dock reopen with a known server does the same. Picking **This computer** from an open list also opens the ghost dashboard first, and the list closes only once that window is showing the painted ghost dashboard, so a window is always present.
- The ghost dashboard is a bundled strict-CSP local page (`electron/skeleton.html`) with its own throwaway session, no preload and no network. It lies over the real window as a separate view, so the real page loads unseen underneath it in the same window. For a remote server it stays until the session check after the first load passes, so a late revocation never shows the server's pairing page. For This computer it stays until the bundled app has loaded. The window shows only after its own page has painted the skeleton, so its first visible frame is the ghost dashboard. Windows puts a newly shown window on screen before Chromium has drawn into it, and a page's own frame signal can come before that frame is on screen. So on Windows the ghost window shows at opacity 0, and turns opaque only once the ghost overlay itself has painted (after the window's own page has also produced a frame), or after 500 ms at most. macOS needs no such step. On Linux a brief native frame (about 50 to 200 ms, in the window system's default color) may appear before the ghost: the window system maps the new window before Chromium's first frame for it, Linux has no window opacity API in Electron, and the other workarounds depend on the window manager. The owner accepted this on November 18, 2026. On macOS a rare single blank frame on a Dock reopen before the ghost is accepted the same way (owner, November 18, 2026): seen once in 7 tries at 87f14e5, not reproduced in 9 at 5b2579d, possibly from a tiling window manager. The overlay then covers that page, and the real page starts loading only after the overlay has painted. Only that one bundled page may load in a remote window, and only before the server's page. The app preload exposes nothing on it. The remote page keeps its isolated session, the bearer rules and no local Electron capabilities.
- Every connect quietly retries network errors and 502, 503 or 504 answers from the descriptor and session checks every 500 ms, for up to 15 s, as T3 does. The one-use pairing-code exchange is never retried. Other limits are unchanged. Late failures after the load keep the PR 1 behavior.
- A failure closes the ghost dashboard and shows the server list with the problem and its **Retry** or **Pair again** button. A protocol mismatch has no button. Closing the ghost dashboard while it connects cancels quietly and opens no list.
- The list still opens on first run (no default), for a damaged saved list, from **Switch server…**, for a failure that needs action, and for pairing. A remote connect started from an open list still shows **Connecting…** in the list.

## PR 2 · Update everything

Build on merged PR 1 and item 1's shared fork release. macOS, unsigned Windows NSIS, and unsigned Linux AppImage get the same sequence. Provider updates are outside scope.

1. Expose only `window.lh.desktopUpdate` to the remote page. Its zero-argument methods are `getStatus()`, `check()`, `download()`, and `install()`. Status reports desktop version, offered target, phase, and a safe error. Main validates the sender's top-level frame and exact selected origin and chooses the official app artifact from the fixed fork feed, using existing electron-updater checksum verification. `install()` opens a native **Update everything** confirmation. Browser Settings retains its server-only flow.
2. Pin the exact shared release and verify the desktop download before requesting a server restart. Ask a behind server through a dedicated authenticated maintenance operation to stage the exact release using the existing launcher trial and rollback. Skip server installation if it is already on target. A server ahead, unsupported updater, or missing artifact stops the run.
3. Show restart progress in the app-owned window. Require both `/api/health` on the exact version and authenticated confirmation that the launcher committed it. A trial can serve health before commit. The maintenance response stays compatible across the restart, and ordinary UI loads still require exact protocol compatibility. Persist the target and selected server before installing the desktop. On relaunch verify the running desktop version and reconnect once to that server. The saved launch default remains in effect for subsequent launches.
4. If server staging fails, rolls back, or times out, keep the desktop at its current version and offer **Retry** or **Switch server…**. If the server commits and desktop installation fails, leave the server at the committed version and offer an explicit retry of the pinned desktop install. A retry checks observed state before restarting either side. A newer target always requires a new run, and installer retries require user action.

### As built

T3 Code reference: 8cf97b5 (`useUpdateEverything.ts`, `updateEverythingRun.tsx`, `SidebarUpdatePill.tsx`, `SettingsPanels.tsx`) and 3ce2145 (`DesktopApplicationMenu.ts`).

- **Bridge.** `electron/remote-preload.cjs` exposes only `window.lh.desktopUpdate`, and only on `https:` pages, never on the ghost dashboard page. `electron/update-everything-ipc.cjs` answers one channel for the current remote window's main frame at its origin, and refuses arguments.
- **Button and Settings.** See [update-control.md](update-control.md). The circle-arrow "Update this app and 1 server" shows only while the server is behind the app's update, as in T3. Otherwise the plain app Download and Install show. Settings there has **Server X** and **This app Y** (T3's labels). The app row's Install opens the same native confirmation.
- **Confirmation.** "Update everything?" / "Update <server> and this app to X." with both steps and the server's running task count, [Update everything] [Cancel]. A server already on X gets "Restart LearnHarness to update to X?" [Restart] [Cancel]. A server newer than X stops with a notice.
- **Order.** `electron/update-everything.cjs`: pin X (re-check once), download exactly X, then `POST /api/updates/install-version {version}` with the paired bearer.
  - The server checks the request at once. It refuses an older, bad, malformed or non-launcher target with 409; otherwise it answers 202 and, in the background, stages X from `v<X>/latest.json` beside its `nightly/latest.json`, checks the SHA-256 and asks the launcher. `pinned: { version, error, id }` in `GET /api/updates` follows it, including a launcher refusal. Each attempt has its own id (also in the 202 body). The app reads `pinned.error` only for the attempt its own request started or joined, so an error left from an earlier attempt is never this run's. A plain Install's launcher refusal isn't written into it.
  - A request with no answer (a lost connection, the transport's timeout, a proxy 5xx) may still have started. If the route itself answers 5xx on 3 polls in a row while `GET /api/updates` answers as the same server process with no attempt for X, the run stops with that status and "Nothing was changed". The app keeps polling and sends it again on the next poll, and the same request is harmless. Only the server's own refusal says "Nothing was changed".
  - The ghost dashboard covers the page with "Updating <server> to X… This can take a few minutes." (only if that server's page is the one open) and post-load rechecks pause for that window only. Switching to another server ends the cover, and the run's end then leaves the other server's window alone.
  - The app polls every 2 s, without the protocol header, until `/api/health` is on X and `GET /api/updates` says `runningVersion` X and `committed: true`. That flag is false while the server is the launcher's uncommitted trial.
- **Failures.** A 404 asks to update the server from its own Settings first. A staging failure or launcher refusal (`pinned.error`), a rollback to the old version, or 32 minutes without the commit (T3's limit; "Couldn’t reach <server>" when no request ever got an answer) shows the list with **Retry** (or **Pair again** after a revocation). A failed app download is a notice before the server is touched; if an older download was shown as ready, the pinned version is offered again instead. The app is unchanged in each case.
- **Restart.** "<server> is on X." / "LearnHarness restarts in 5 seconds to finish updating." [Restart now] [Later]. The dialog closes itself after 5 s and restarts. Later keeps the same window: the cover goes and the page shows the updated server, loaded exactly once (a reconnect would close the only window first, and Windows and Linux quit then). If the page already reloaded itself under the cover (#264), nothing more; otherwise Later claims X in the page's own once-per-version memory, then reloads it, so the page doesn't reload itself on top. The next run only restarts the app. Before installing, `userData/update-everything.json` saves the open server (the one to reopen), the updated one and X. The next launch reads it once within 10 minutes (T3's limit) and reopens that server instead of the default. If the app isn't on X (the installer refused it), it offers the app-only retry from PR 2 item 4, once: "The app update didn’t finish." / "LearnHarness is still on Y and <server> is on X. Install LearnHarness X again? Only this app restarts." [Try Again] [Later]. Try Again checks the feed for exactly X, downloads and installs it, with no server request; a newer version needs a new Update everything. The real feed reads `v<X>/` (`NightlyProvider.pinned`); the `LH_UPDATE_FEED` test feed reads its own `v<X>/` folder the same way. If a check already in flight (the startup check) answers with the newest version, it checks once more, pinned. The same offer follows an app install that fails in the same session after the server committed. Later changes nothing. The offer is made once. Try Again marks its saved result as a retry, so when its install fails too (seen only after the relaunch on the old version, on all three platforms) the next launch doesn't offer it again but says the same failure text below. A failed Try Again clears the saved result and says "Couldn’t install the app update." / "LearnHarness is still on Y and <server> is on X. Use Update everything to try again." (owner wording).
- **Menu.** While connected to a server, **Check for Updates…** stays enabled and uses T3's native dialogs for this app only: up to date, available (Download / Later), downloading, ready (Restart / Later), check failed, unavailable. As in T3, the heading ("You're up to date!", "Update check failed", "Updates unavailable") is the dialog `title`, which Electron ignores on macOS: there the sheet shows only the message and detail. It's the way out when the app is too old to open its server. During a run (or its confirmation) it only says "Update everything is running.", and the plain download and install wait, so nothing installs another version mid-run.
- A page reload during the run (for example after the server's own update) stays under the cover.

## Merge gates and proof

Each PR requires passing CI Check, one fresh review round, and an independent `PROVED` comment naming the final head. Run heavyweight builds and runtime proof on the ThinkPad, one slot at a time, with isolated profiles and synthetic services.

For PR 1, drive first-run setup in both modes, paste and manual pairing, switches between local and two remote fixtures, default selection and relaunch, revocation, offline recovery and protocol mismatch. Observe the remote server's rendered UI, an ordinary 404 staying in the window, previous streams closing, and the bundled server stopping. Verify that a damaged saved list leaves local setup usable and that resetting permits new pairing. Check that cookies are absent on preflight, that credentials cannot follow redirects, and that remote frames lack local capabilities. Verify external links and a provider sign-in action open the system browser without its paired bearer. Exercise a synthetic ChatGPT browser callback, duplicate and invalid callbacks, bind failure, a returned redirect pointing to an already occupied port, and immediate retry after desktop cancellation. Exercise web paste-back separately. Use no real accounts.

Set `LH_DEBUG_FIRST_FRAME=1` to log first-frame timings (milliseconds since process start) to stdout and `userData/logs/main.log`: window creation, each `show()` call with its call site, the native show event, the Windows opacity steps and fallback, `ready-to-show`, page loads, frames produced, the 1 s fallback, the overlay, the real page load, the reveal and the list closing.

For the quiet launch, relaunch a profile with a saved default for This computer and for a remote fixture, and confirm the following. No server list opens. The ghost dashboard shows its status line in the main window from the first frame and stays over the remote page through the session check after load. A slow-starting fixture answering 503 connects within 15 s without a problem. Revoking the bearer between the two checks shows the list with **Pair again** and never the pairing page. An offline fixture shows the list with **Retry** after 15 s. Closing the ghost dashboard cancels without a list. Dock reopen behaves the same on macOS, and a light theme gets the light colors.

For the setup screen, drive both tiles on a fresh profile, paste a pairing link and a bare address without a scheme, and check both error messages, the light theme and reduced motion.
