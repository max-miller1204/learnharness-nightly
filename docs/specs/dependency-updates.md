# Dependency updates (Dependabot)

Status: approved by the owner on 2026-11-17.

Goal: keep the fork's dependencies current on its own (upstream is mostly inactive), with little churn: one grouped PR a week for minor and patch updates, one PR per major bump, and security fixes right away. Covers npm (root and all five `plugins/*` packages) and GitHub Actions, including Pi.

## Decided by the owner

1. A full bot: version updates and security updates.
2. Weekly, grouped: one PR per week for all minor and patch updates (per ecosystem).
3. Major bumps: one PR each.
4. Security updates: right away, outside the weekly batch.
5. Plugins: commit each SDK plugin's generated `.sdk/package.json`, plus a CI check that it matches the generator (see "Plugins").
6. Pi and typebox get their own group, and an agent finishes those PRs (see "Pi").
7. Minor/patch PRs (weekly batches and security PRs) auto-merge when `Check` is green, queued by a workflow using the fork bot App token.
8. Only majors (and the Pi group) wait for an agent: one review round plus a `prove-learnharness` run, then the agent queues `gh pr merge <N> --auto --squash`.
9. The PR-Agent Docker image stays manual, with a note (Dependabot can't update `docker://` refs).
10. The two security settings are turned on with `gh api` right after this PR merges, and read back to confirm.

## Adopted from T3 Code (veto any)

T3 Code (`pingdotgg/t3code`) uses **Dependabot**, not Renovate. It has no `dependabot.yml`: it runs only security updates from the repository settings, grouped into one PR per ecosystem across all directories ("bump the npm_and_yarn group across 5 directories"), titled `chore(deps): ...`, merged by a person. Taken from it:

- Dependabot rather than Renovate.
- Security fixes grouped into one PR per ecosystem across all directories (here through a `groups` entry with `applies-to: security-updates`, so the config, not a repository toggle, sets it).
- Commit and PR titles `chore(deps): ...` (`chore(deps-dev): ...` for dev dependencies), with Dependabot's default labels (`dependencies` plus the ecosystem).

T3 has no version updates, so the schedule, grouping and merge gate come from the owner's decisions above.

## `.github/dependabot.yml` (new)

Two entries, one per ecosystem. Both use:

- `schedule`: `interval: weekly`, `day: monday`, `time: "06:00"`, `timezone: Etc/UTC`.
- `commit-message`: `prefix: chore`, `prefix-development: chore` (npm only), `include: scope`.
- Dependabot defaults otherwise: `open-pull-requests-limit` 5 per entry (the first weeks' majors trickle in five at a time), `rebase-strategy: auto`, the default 3-day cooldown on new releases for version updates (security updates skip it), and `versioning-strategy: auto` for npm (it raises the range in `package.json` and updates the lockfile).

Groups, in order (a dependency joins the first group it matches):

**npm** (`directories: ["/", "/plugins/*"]`):

| Group | Matches | PRs |
|---|---|---|
| `pi` | `@earendil-works/*`, `typebox`, all update types | One a week |
| `npm-minor-patch` | everything else, `update-types: [minor, patch]` | One a week, across all six directories |
| `npm-major` | everything else, `update-types: [major]`, `group-by: dependency-name` | One per package, across all directories (TypeScript 7 is one PR, not five) |
| `npm-security` | `*`, `applies-to: security-updates` | One per ecosystem when an advisory needs a fix |

**github-actions** (`directories: ["/", "/.github/actions/*"]`, so workflows and the two composite actions both count):

| Group | Matches |
|---|---|
| `actions-minor-patch` | `update-types: [minor, patch]` |
| `actions-major` | `update-types: [major]`, `group-by: dependency-name` |
| `actions-security` | `applies-to: security-updates` |

Pinning works as it is today. Actions on a major tag (`actions/checkout@v7`) get a PR only when a new major tag exists. SHA-pinned actions with a version comment (`actions/create-github-app-token@<sha> # v3.3.0` in `.github/actions/fork-bot-token`) get the SHA and comment updated together. The PR-Agent image (`docker://pragent/pr-agent:...@sha256:...`) isn't supported by Dependabot (GitHub's docs: only repository-syntax actions). It stays manual, and a comment in `pr-agent.yml` and a line in `docs/fork-workflow.md` say so.

Changing `.github/dependabot.yml` needs no GitHub App or extra permission. It's an ordinary file in a PR, and it isn't under `.github/workflows/`. Dependabot reads it from `main` only, so version updates start once this PR merges.

## Plugins

coding-questions, drawing-pad, rich-code-blocks and ui-showcase depend on `"learnharness-plugin-api": "file:.sdk"`. `.sdk/` is generated by `npm run sdk` (`scripts/build-plugin-types.mjs`) and ignored, so Dependabot aborts on those directories: "path based dependencies could not be retrieved: learnharness-plugin-api" (reproduced with the Dependabot CLI v1.97.0 on `/plugins/drawing-pad`). With a committed `.sdk/package.json`, the same run gets past file fetching.

- Commit `plugins/<id>/.sdk/package.json` for those four plugins with `git add -f`, byte-identical to what `npm run sdk` writes. Only that file: the `.d.ts` files stay generated and ignored. The plugins' `.gitignore` files stay as they are, because they ship in the plugin-authoring bundle. Nothing that builds plugins or the authoring kit copies `.sdk/`.
- CI check, in the always-running `Lint` job, right after `setup-deps` (which has just run `npm run sdk` in every plugin): every plugin whose `package.json` has an `sdk` script must have a tracked `.sdk/package.json`, and `git diff --exit-code -- 'plugins/*/.sdk/package.json'` must be clean. Otherwise it fails with a message saying to run `npm run plugins:setup` and commit the result.
- `docs/development.md` (the `plugins:setup` paragraph) says the `.sdk/package.json` is committed.

**Interim.** The owner plans a separate roadmap item to publish the plugin API (`learnharness-plugin-api`) as a proper versioned package for outside plugin authors. It replaces these committed files. Not built here.

## Pi

Root pins `@earendil-works/pi-ai` and `@earendil-works/pi-agent-core` exactly (1.4.0; 1.5.2 is out) and `typebox` at `^1.3.27`. The generated `.sdk/package.json` declares the root's values as peer dependencies, so the four SDK plugins' lockfiles pin Pi and typebox too. A root-only bump, which is what Dependabot makes, breaks the plugins' `npm ci`. Tested: Pi 1.5.2 fails with "lock file's @earendil-works/pi-ai@1.4.0 does not satisfy 1.5.2", and typebox `^1.4.7` fails the same way. So the `pi` group comes first, which keeps Pi and typebox out of the weekly batch so the batch stays green.

The `pi` PR arrives red by design. An agent finishes it: after `npm install` at the root, run `npm run sdk && npm install` in each SDK plugin to regenerate the four `.sdk/package.json` files and refresh the plugin lockfiles, adapt code to Pi's changes, push to the Dependabot branch, then do one review round, a `prove-learnharness` run, and queue the merge. Once someone else pushes to its branch, Dependabot stops rebasing that PR. Comment `@dependabot recreate` to start over.

**Interim**, like the plugins section: once the plugin API is a versioned package, plugins can accept a Pi peer range, and the `pi` group can probably go green on its own.

## Merge gate for bot PRs

Bot PRs get full CI and the required `Check` (CI uses no secrets, so Dependabot's restricted runs are enough). PR-Agent skips them because it ignores bots.

| PR | Gate |
|---|---|
| Weekly minor/patch batch (npm or Actions) | Auto-merge (squash) when `Check` is green |
| Security PR whose highest change is minor or patch | Auto-merge (squash) when `Check` is green |
| Major (one each), or a security PR that needs a major | Agent: review round, `prove-learnharness`, then `gh pr merge <N> --auto --squash` |
| `pi` group, or any PR that touches Pi or typebox | Agent finishes it (see "Pi"), then the same as a major |

### `.github/workflows/dependabot-auto-merge.yml` (new)

- Trigger: `pull_request_target` (`opened`, `reopened`, `synchronize`), so GitHub always runs `main`'s copy of the workflow. A Dependabot PR that bumps an action used in this file (`fetch-metadata`, `checkout`) can't run the new, unreviewed version in the job that gets the App key; it runs only after it merges. These runs read the normal Actions secrets, unlike Dependabot `pull_request` runs. The workflow never checks out or runs the PR's code.
- Runs only when `github.repository` is this fork and both the PR author and `github.actor` are `dependabot[bot]`. A PR from anyone else, or a push by an agent or a person to a Dependabot branch, never runs it.
- One run per PR at a time (`concurrency` keyed on the PR number, `cancel-in-progress`), so the newest event decides.
- `permissions: contents: read, pull-requests: read`. Everything that writes uses the App token.
- Steps:
  1. `dependabot/fetch-metadata@25dd0e34f4fe68f24cc83900b1fe3fe149efef98 # v3.1.0`: `update-type` (the highest change in the PR) and `dependency-names`.
  2. `actions/checkout@v7` of the **default branch** (not the PR), `persist-credentials: false`. The token step then runs `main`'s copy of `.github/actions/fork-bot-token`, not one a bot PR edited (Dependabot does bump the SHA inside it).
  3. `./.github/actions/fork-bot-token` with `secrets.FORK_BOT_CLIENT_ID` and `secrets.FORK_BOT_PRIVATE_KEY` (the existing Actions secrets).
  4. Eligible when `update-type` is `version-update:semver-minor` or `version-update:semver-patch` and no dependency name is `@earendil-works/*` or `typebox`. If eligible, `gh pr merge --auto --squash <url>`. If not, log why, and if auto-merge is on (a rebase made it ineligible) turn it off with `gh pr merge --disable-auto <url>`.
- Why the App token: when GitHub's built-in token turns on auto-merge, the merge's push to `main` starts no workflows, so no CI on `main` and no nightly. With the App token, the merge runs CI and the nightly like any other.
- The workflow isn't part of `Check`. If it fails, the PR just waits.
- Changed after the review round: the spec first used `pull_request` with the App values copied into the Dependabot secrets store. The review showed that this runs a bot PR's bumped actions next to the App key, so it moved to `pull_request_target` (approved), and the Dependabot secrets step went away.

## Upstream Sync PR and lockfile conflicts

Low risk, since upstream is mostly inactive. When the hourly Sync PR and a Dependabot PR both touch `package-lock.json` (or `package.json`):

- Dependabot PR open, Sync PR merges first: Dependabot rebases its own PR automatically (`rebase-strategy: auto`) and regenerates the lockfile change on the new base. It can't do that once someone else has pushed to the branch; then use `@dependabot recreate`.
- Dependabot PR merged first: the Sync PR may conflict in the lockfile. Resolve it in the Sync PR as today: take upstream's `package.json` intent, then regenerate the lockfile with `npm install` rather than hand-merging it.
- An upstream Pi or typebox bump arriving through the Sync PR needs the same four `.sdk/package.json` files and plugin lockfiles regenerated in that PR. The new `Lint` check points at it.

## Verification

1. Validate `.github/dependabot.yml` against the SchemaStore `dependabot-2.0` JSON schema.
2. Dependabot CLI (v1.97.0, local Docker): a plugin directory fails at file fetching without the committed `.sdk/package.json` and gets past it with one. (Full local update runs couldn't finish on this machine: the updater can't reach the CLI's local API, an environment limit. So the live run in step 5 is the end-to-end proof.)
3. The new `Lint` check passes on this PR and fails on a scratch branch where a committed `.sdk/package.json` is changed (then the branch is deleted).
4. CI `Check` green, one independent review round, and a `prove-learnharness` run (the change reaches no app surface; the `.sdk/package.json` files are build inputs, and plugin typecheck and tests run in CI).
5. After merge: Dependabot runs on `main` (Insights → Dependency graph → Dependabot shows each directory as checked, with no errors), and the first PRs open: a `npm-minor-patch` batch, a `pi` PR (red, as designed), and up to five majors. The auto-merge run on the batch PR queues auto-merge. Both security settings read back as enabled.
