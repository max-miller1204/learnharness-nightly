# Verify LearnHarness

Proof means you watched the running app do the thing. Tests passing, code reading well or a build succeeding is not proof.

Run this at the end of a change, before you say done.

Every check has three parts: the surface you drive, the answer key that says what right looks like, and the comparison between them.

All commands below run from this skill's folder (`.claude/skills/prove-learnharness/`). Knobs (speed, timeouts, model) live in `scripts/knobs.env`; answer-key budgets live in `budgets.json` and only the user edits them.

## Scope

By default, prove the current change: uncommitted work plus the commits on this branch since it left `origin/main`.

```bash
git fetch origin main -q
node scripts/scope.mjs        # the diff, the surfaces and tiers it reaches, and the exact plan to run
```

`scope.mjs` runs `git merge-base HEAD origin/main`, `git diff --name-only <base>` and `git ls-files --others --exclude-standard`, then applies the map below and prints the plan: only the surfaces and tiers the diff reaches.

Run the whole plan in one go with `scripts/run-plan.sh <slug> [same args as scope.mjs]`: it makes the run folder, runs every planned step in order, carries on past failing checks (they are evidence), always cleans up, and prints a summary (each compare's result, the failed commands) with the run folder on its last line. If the change itself fails to build, start or launch, it stops and reports BROKEN (back to the builder); if the base build, the environment or a planned surface fails, it stops as BLOCKED. Files `scope.mjs` can't map stop it as BLOCKED before anything runs: decide by hand and add a rule. `--base <ref>` applies to the whole run. Exit 0 all checks passed, 1 a check failed or the change is BROKEN, 2 BLOCKED, 3 no app surface, 4 the scripted checks passed and a step by hand is next (the summary's `MANUAL` line: a mobile device proof, or driving a changed CI script's CLI; not BLOCKED and not a verdict). For a mobile change the scripted part is `scripts/mobile-checks.sh`: the app's unit tests and this skill's phone checks, under Node 22 (mise's `node@22`, or `MOBILE_NODE_BIN`; any other major is BLOCKED). The plan has stopped its instances by then, so drive a device recipe in a run folder of its own (`scripts/new-run.sh <slug>-device`, then `start.sh` there with the recipe's scenario) and name both run folders in one receipt. Then read the evidence: a script pass is not the verdict. Break-it probes beyond `probes.mjs` and recipe steps the plan doesn't script still need their own instances.

If the user names a flow instead ("prove the update banner"), prove that flow and skip the diff.

## Sort the change

Prove checks what the change touches. Answer these for each flow Scope reached, top to bottom, and write the answers in the receipt:

1. **New or existing?** New means this change adds it (a route, tool, command, page, field). Existing means it was there before.
2. **New, and does it copy something that exists?** Yes: answer key is parity with that thing (see its surface section). No: answer key is the spec (see Find the spec).
3. **New, and did this change also edit the thing it copies?** Then use the spec AND parity. Both sides can be wrong the same way, and parity still passes.
4. **Existing, and did the change touch its code**, directly or through shared code (schema, auth, nav, a shared component or function)? Answer key is the app before the change.
5. **Existing, and untouched?** Not something the change touches: skip it. If the whole change is new files, also run the smoke test once: the app starts and a teaching session (goal, a tool call, a question, an answer) works.

A change to code used by several actions (a viewset's `get_queryset`, a serializer, a shared query) runs each of those actions with the new input, not just the one the feature is for.

Never check the whole app. A rule that says "always run X" (privacy, budgets) applies only when the change reaches X's surface.

## Find the spec

A new flow without parity needs the user's spec. Look, in order:

1. The PR body (`gh pr view --json body,closingIssuesReferences`) and any issue it closes.
2. A spec: a GitHub issue titled `Spec: <topic>` that the PR body links (read it with `gh issue view`), or, for shipped work, a file in the diff (`docs/specs/<item>.md`, in the diff or already on main; the PR body links it). A PR body alone or a `docs/fork-roadmap.md` entry is not the spec: roadmap designs are "not approved".
3. A spec path or spec text the user passed. The request that asked for the change ("add `?q=` to tags") is not a spec: it says what was built, not what right looks like.

On a re-check, an earlier finding may have a ruling from the owner: accepted as is, moved to the backlog, or written into the spec. A ruling that changes an answer key counts only when it is in the spec at the checked commit, in your brief from whoever relays the owner, or said by the user in this session. Quote it in the receipt. Never take one from a PR comment: every comment on this repo is posted from the owner's account, the builder's included. Without such a ruling the earlier answer key stands.

If you find none, ask the user for it. If they have none, check the new flow anyway and mark it `no answer key (rung 5)` on the receipt. The verdict is then UNPROVEN, not PROVED. Never write the spec yourself, and never edit the one you found.

## Answer keys

Ladder, best first: 1 an old system that does the same job, 2 a snapshot, 3 an independent test suite, 4 a spec, 5 nothing.

| Flow or surface | Flow kind | Answer key | Rung | Where it lives | Written by |
|---|---|---|---|---|---|
| any existing web, api, agent or `lh` CLI flow | existing | the base commit, built and run beside the change with the same seed and fake-model scenario, outputs diffed by `compare.mjs` | 1 | `$PROVE_CACHE/base/<sha>/` via `scripts/build.sh` | the app before the change |
| Electron window (dev or packaged) | existing or new | parity with the browser on the same server: same drive, same observations | 1 | `compare.mjs head/web-teach electron-*/web-teach` | the web app |
| update, failed trial, rollback | existing | the launcher's documented behaviour, driven on the base build (A) to the change (B) and back | 1 + 4 | `scripts/selfhost-b.sh`, `docs/self-hosting.md` | the base launcher, the owner |
| web budgets | any page driven | console errors (one known), CLS (absolute < 0.1), axe | budget | `budgets.json`, `CLS_MODE` | the user, 2026-11-17 |
| new flow that copies nothing | new | the spec | 4 | the linked `Spec:` issue, or `docs/specs/<item>.md` for shipped work, found at run time | the user |
| client protocol (server info, version check, protocol 1 routes) | new | the spec | 4 | `docs/specs/client-protocol.md` | the user |
| mobile beta | new | browser parity and the spec for phone-only flows | 1 + 4 | [mobile beta](references/features/mobile-beta.md) | the web app and the owner |

- **Never edit an answer key to make a check pass.** If the app and the answer key disagree, the verdict is BROKEN; only the user changes an answer key.
- **Compare against the answer key, not your idea of right.** Where a flow has none, say so on the receipt.
- **A spec line that says an area is "not changed"** makes that area an existing flow. Run the same input on the base commit and on the change, and compare the two outputs with each other, not with the spec. Any difference is BROKEN until the user approves it, even when the spec seems to allow it. Base `[3, 4, 6]` and change `[]` is BROKEN, not noise.
- **There is no "PROVED with a flag".** A question for the user is BROKEN until they answer it. A parity difference is BROKEN unless it is listed under Known and deliberate.
- **A snapshot shows "same as before", not "correct".** If the change is meant to alter a snapshot, the step is BROKEN until the user approves a new one.

## Check in a fresh agent

The agent that made the change knows what it meant to build, so it tends to see what it expects. Do Scope, Sort and Find the spec yourself, then, if you can start a sub-agent (the Agent tool in Claude Code, a subagent in Codex), hand the proof to a fresh one. Give it only the flows, the surfaces, whether each is new or existing, the answer keys, and the name of this skill. Not your plan, your reasoning or what you think the change does. Ask for PROVED, BROKEN, BLOCKED or UNPROVEN and the receipt path.

If you can't start a sub-agent, run the proof yourself and write `Checker: same agent (not independent)` on the receipt.

## Start

```bash
RUN=$(scripts/new-run.sh <slug>)          # .prove-it/runs/<UTC>-<slug>/, reports live leftovers
scripts/build.sh "$RUN" both              # head + base in parallel; base cached per SHA, head reused if unchanged
H=$(scripts/start.sh "$RUN" head)         # fake model + standalone server on free ports, throwaway HOME/data/auth
B=$(scripts/start.sh "$RUN" base)
```

`next build` runs only in one of `MACHINE_BUILD_SLOTS` machine-wide slots (default 2, lock files in `$PROVE_CACHE/build-slots/`, shared by every worktree and child); a build waits for a free slot up to `BUILD_SLOT_WAIT_S`. Each `start.sh` returns in about 2 s with the path of an `instance.env` (URLs, ports, data dir, model log). The server runs with `env -i` (no ambient keys) and `LH_IGNORE_ENV_KEYS=1`. `PROVE_MODEL=claude-code scripts/start.sh ...` swaps the fake model for your signed-in claude CLI (opt-in, costs usage, keeps your real HOME).

Ready when: `/api/health` answers `ok` and `/api/models` lists all three slots seeded (`start.sh` waits for both and fails otherwise).

Never drive an instance you didn't start. Every process this run started has a pid file under `$RUN` and leads its own process group; `health.sh` checks the port belongs to that group.

## Health check

`scripts/health.sh "$H"`: checks the pids are alive and own the port, then prints side, URL, build (worktree tree hash or base SHA, and the baked version, `...nightly.20000101.2` for head, `.1` for base), data dir and session count, model slots and `/api/health`. Run it before the first drive and again after anything surprising.

## Surfaces

One section per surface. `/create-prove-it` adds a section when the app gains a surface.

### Web (primary)

**Drive**: `node scripts/web-teach.mjs "$B"`, then `"$H"`, then `node scripts/compare.mjs "$RUN/base/web-teach/result.json" "$RUN/head/web-teach/result.json" --out "$RUN/compare-web.md"`. Run `scripts/ensure-axe.sh` once first. Run `node scripts/web-delete.mjs "$H"` for the deletion contract in #343 and item 4 of `docs/specs/polish-first-load.md`. Puppeteer-core drives `/usr/bin/google-chrome` with `data-testid` selectors. Details: [references/web.md](references/web.md).

**Copies**: nothing. The base commit is its answer key for existing flows.

**Done looks like**: the session appears, both reads reach the model with their files' exact text (the fixture, and a second one with no final newline), the question card shows the scenario's options, the answer reaches the model and its reply shows, the record on disk holds all of it, a reload shows it, deleting removes it from sidebar, API and disk; and the budgets hold. Assert all of it, not just the field the change is about. It adds to the answer key, never overrides it.

**Could fool you**:
- the transcript can show text before it is stored: `web-teach.mjs` also reads `data/chats/<id>.json`.
- the question card shuffles its options on purpose: compare them as a set.
- a single-select option's text includes its letter badge ("ABlue", since c3ff55ff): a read of `textContent` sees no "Blue", the pick never happens and the drive times out on both sides (every plan from #322 to this fix was BLOCKED that way). `scripts/question-options.mjs` reads the label without the badge and the letters on their own (`optionLetters`, diffed against base).
- sidebar, API and disk removal can all pass while the deleted transcript stays mounted or stale reads return 404. `web-delete.mjs` checks the open view, an older Back entry, and every session API 404 from confirmation onward for single, folder and graph source deletes.
- one session hides "lists only the newest": the drive uses a unique goal per run and checks the count before and after.
- one session also hides the list's order: a list sorted oldest first passed every drive (audit 2026-11-21). `api-check.mjs` makes three sessions, then a turn on the first, and records the order before and after (`listOrder`); `web-teach.mjs` does the same in the rendered sidebar (`sidebarOrder`). The turn tells ordering by last activity from ordering by creation.
- a Retry button that is there but does nothing passed a probe that only looked for it (audit 2026-11-21): `probes.mjs` C presses Retry by mouse and from the keyboard (focus, Enter), and each counts only once its one `POST /api/chat` stream has closed, the question card is up and Retry is gone.

### API (`app/api`)

**Drive**: `node scripts/api-check.mjs "$B"` and `"$H"`, then `compare.mjs` on `api-check/result.json`. Read routes (status plus body shape), refusals (foreign Host, cross-site Origin and fetch metadata, unknown id, bad JSON, empty input, delete without mode), a create/list/delete round trip on disk, and a failing model (fake `http500`) that must end the turn with a recorded error. Run `scripts/api-pricing.sh "$RUN"` for the #345 pricing contracts. Details: [references/api.md](references/api.md).

**Copies**: nothing (the web UI is its main caller).

**Done looks like**: every read route answers its expected status with the base's shape, every refusal still refuses, the round trip leaves no record, the model failure is recorded as an error.

**Could fool you**:
- a catalog change during a call can misprice persisted usage even when every response has the expected shape. The pricing drive holds an API call across a fake catalog refresh and checks the dispatch rate in the saved call. It also reads the plugin usage ledger for absent router placeholder cost, explicit known-free zero and priced cost.
- `fetch` can't forge `Host`: `api-check.mjs` uses raw `http.request` for that probe.
- shapes, not values, are diffed: a value change in a read route needs a recipe step that asserts the value. The list's order is one such value: `listOrder` (three sessions, labelled) is diffed against base, and a reversed sort fails it.

### Agent tools (`src/agent`)

**Drive**: the teaching-session drive above, with the fake model playing `scenarios/<name>.json`: exact tool calls (`read`, `probe`, ...) and their results land in `model-requests.jsonl`. A change to a tool adds a scenario that calls it with the new input, plus a failing variant (`/__prove/fail?mode=http500|broken-stream|hang`). Real-model behaviour: `PROVE_MODEL=claude-code` and `node scripts/web-real-turn.mjs "$H"`. Details: [references/agent.md](references/agent.md).

**Copies**: nothing. The base commit runs the same scenario.

**Done looks like**: the tool result the app sent back to the model is exactly what the tool should produce for that input (read it in `model-requests.jsonl`), and the UI and the stored record show the same.

**Could fool you**:
- the fake model never judges content: a prompt change needs the real-model check and the spec.
- a scenario rule that never fires falls through to the fallback reply: `observations.modelRules` must list every rule you expected.
- a tool result that "contains" the right text can still be wrong: a `read` that dropped the last line of a file without a final newline passed a contains check on a fixture that ends in one (audit 2026-11-21). The drive reads two fixtures, one with no final newline, and requires each tool result to equal its file byte for byte (`observations.readResults`).

### Self-hosted server and `lh` launcher (`selfhost/`)

**Drive**: tier A (seconds): `scripts/selfhost-a.sh "$RUN" base` and `head`, then `compare.mjs` on `selfhost-a/result.json`. Tier B (about a minute after builds): `scripts/selfhost-b.sh "$RUN"` installs the base build through `install.sh` under a throwaway `lh-prove-<hash of the run path>.service`, updates to the change, fails a broken trial, and `lh rollback`s. Details: [references/selfhost.md](references/selfhost.md).

**Copies**: nothing; the base build's launcher is the "before".

**Done looks like**: every step in `$RUN/selfhost/steps.log` is ok: healthy on each version, `service-state.json` committed or rolled-back as expected, the broken version marked bad, a backup named after the old version, the seeded session alive after each switch, and the real `learnharness.service` unchanged.

**Could fool you**:
- `/api/health` can answer from the old server for a moment: tier B waits for the version AND the state file.
- with "Automatic updates" on, the server can install a downloaded update by itself before `lh update --now`: both paths must end on the same state.

### Electron desktop (Linux)

**Drive**: `E=$(scripts/electron.sh "$RUN" dev)` (dev shell on the head server) or `packaged` (`electron-builder --linux dir`, about 10 s with a warm cache), then `node scripts/web-teach.mjs "$E"` and parity with the browser: `node scripts/compare.mjs "$RUN/head/web-teach/result.json" "$(dirname "$E")/web-teach/result.json" --allow 'apiCalls=GET /api/updates 200' --allow 'apiCalls=GET /api/subscriptions 200' --skip desktop`. Details: [references/electron.md](references/electron.md).

**Copies**: the web UI on the same server (parity, rung 1); for desktop-only output, the base commit's desktop window (rung 1).

**Done looks like**: the window shows the app with `window.lh` present and reporting this machine's platform, the full teaching drive passes with the same observations as the browser, and the desktop-only observations match the base desktop window.

**Could fool you**:
- the dev shell skips the packaged server spawn, the desktop secret and the updater: changes there need `packaged`.
- runs use `--no-sandbox` (ELECTRON_NO_SANDBOX=1): sandbox-only bugs are not covered.
- browser parity can't see the bridge or the native window chrome: a bridge reporting `darwin` on Linux (macOS gutters, native buttons over the header) passed parity (audit 2026-11-21). The drive asserts the platform matches the host, and `compare-desktop.md` diffs the desktop-only observations against the base desktop window. The plan opens the base desktop window for every desktop change, including the web files that lay out the window's chrome (Scope map).

### Varies by and deliberate

- **Varies by**: build mode (production standalone here; `next dev` is not proved), signed in or out (every request needs a login; `APP_TOKEN` in instance.env), desktop vs browser (desktop bearer session, native updater, desktop-owned subscriptions), model provider (fake custom endpoint vs Claude Code CLI). A flow isn't proved while a variant the change reaches is unproven.
- **Known and deliberate**: the desktop window never calls `GET /api/updates` or `GET /api/subscriptions` (native updater, desktop-owned subscriptions). `GET /api/claude-code` answers 403 until Claude Code is turned on. `GET /api/jobs` needs `?chatId=`. The probe card shuffles options. Console: `/api/stt/token` 503 with no Deepgram key (see `budgets.json`).

### Verifying a bug fix

Run the probe that shows the bug on the unchanged code first and record the value that shows it (status code, stored field, console line or `steps.log` line). Apply the fix and run the same probe again. Both values go in the receipt. If the bug doesn't reproduce first, stop and say so. The base instance is the unchanged code: run the probe on `$B` and `$H`.

## Features

Each user feature has a recipe in `references/features/<feature>.md`. [references/features/README.md](references/features/README.md) lists them, with the seed data and preconditions every recipe starts from. Read only the recipes for the flows Sort picked.

A recipe says how to reach and drive a feature, never what right looks like: that is the answer key. Its sections, in order: a title and one paragraph on what the user can do, `Sub-features` (a short id and one line each), `How to get to it` (every entry point a user has, such as a button, a shortcut, a CLI command), `Driving it` (preconditions, then each action paired with its exact command and what you can see afterwards) and `Gotchas`. Proving one entry point does not prove another.

## Try to break it

After the happy path passes, run at least one probe that matches what you changed. `node scripts/probes.mjs "$B"` and `"$H"`, then `compare.mjs` on `probes/result.json`, script the first and third:
- model failure mid-turn: `curl -X POST "$FAKE_CONTROL/__prove/fail?mode=broken-stream"` (or `http500`, `hang`), send a turn, expect a recorded error, "Something went wrong" with Retry, a usable composer and a working follow-up; reset with `mode=none`. Then press Retry on a failed turn (`http500`): expect a `POST /api/chat`, the turn completed and the banner gone.
- delete the session you are viewing (open it, right-click its row, Delete): expect no 404 for the deleted session (`/api/chats/<id>`, `/api/chats/<id>/side-chats`), home after, and Back not reopening it. Any such 404 is BROKEN. Right after a turn starts, the delete is refused while the turn runs: `DELETE` answers 409 and the dialog says "A turn is running in this session", the session stays, and Try again after the turn ends deletes it with the same expectations.
- doing it twice: on the question card press Enter twice on Submit answer; expect one answer in `data/chats/<id>.json`.
- cold start, in its own run folder (one instance per side per run): `C=$(scripts/new-run.sh cold); PROVE_SEED=0 scripts/start.sh "$C" head` starts with no model configured; `/chat/new` must show the setup call to action (`data-testid="setup-cta"`), not an error page, and a turn must answer 422 `models_not_configured`; then `scripts/stop.sh "$C"`.
- selfhost: a broken version is already probed by tier B; for launcher changes also try `lh use <bad version>` and `lh rollback` with no previous version.
- a sibling flow that should behave the same: practice sessions (`new-session-practice`) for a teaching-session change.

```
Verdict: PROVED | BROKEN | BLOCKED | UNPROVEN
Checker: fresh sub-agent | same agent (not independent)
Scope: diff <base sha>..<head sha> (+ uncommitted: yes|no) | flow "<name>"
Changed files: <list, or "n/a" for a flow>
Surfaces driven: <web, api, ...>
Instance: <url or binary, version or commit, port>
## What the change touches
- <flow> -> new|existing, copies <thing|nothing> -> answer key <name> (rung <n>)
- <smoke test of the existing app, if the change is only new files>
## Steps
1. [PASS|FAIL|BLOCKED] <flow> (new|existing) <what you did to the running app> -> <what it showed> vs <answer key it was compared with> (<evidence file or inline output>)
## Probes
- [PASS|FAIL] <probe> -> <result>
## Retries and fixes
- <step that failed first> -> <why: caused by the change | skill step wrong | environment> -> <the command, port, selector or auth step that finally worked>
## Not covered
- <item> -> <why> -> <the unlock that would cover it, or exact steps for a human>
## Left behind
- <test data from this run still present, or "none">
```

Fill "Retries and fixes" honestly, even on a PROVED run. A step that failed for a reason unrelated to the change is how the next agent learns this skill has drifted.

An existing flow whose output differs from the base commit makes the verdict BROKEN, even when the new feature works. Report it as a failing step, never as a side note under a passing verdict.

UNPROVEN means every step passed but at least one new flow had no answer key (rung 5). It leads Couldn't prove.

PROVED only if every step passed, every step was compared with its answer key, and every promised behaviour has a step you ran and watched. Reading code doesn't count. Ambiguous output is BROKEN with the raw capture attached.

- **A step counts only if its evidence shows a change you can name.** A step that changes state needs evidence from before and after (screenshot, page text, count, output). If they're identical, the step did nothing: BROKEN.
- **Check the evidence shows the target** before you cite it. A modal or banner can cover the page, and a background tab can render blank. Clear it and capture again.
- **A broken verifier is BLOCKED, never a pass.** A crash, missing file, empty output, auth error or path error means BLOCKED with the raw error attached. Never "nothing found, all fine". A missing key or service is BLOCKED too: never stub around it and report green.
- **Say when a check got weaker.** If it fell back to a lesser version (a free item instead of a paid one, stored state instead of the live flow, one browser when another is the risk), write that under Not covered.

## Report to the user

End with a short message, not just a path. The user may not be able to open your files.

```
<PROVED | BROKEN | BLOCKED | UNPROVEN>: <what was proved, one line>
Couldn't prove: <each item, why, and the unlock or the steps for a human; "nothing" only if every promised behaviour has a passing step>
Evidence: <the one screenshot that shows the feature (attach or embed it if your tool can), the key numbers (budget results, counts, status codes), the key output inline>
Answer keys: <each flow and what it was checked against, e.g. new picker against the spec, recording page against main; flag any that were "nothing">
Receipt: .prove-it/runs/<run>/receipt.md
```

Put "Couldn't prove" before the evidence, every time, even on PROVED. A pass that hides what it skipped reads as full coverage.

## Merge gate (PRs)

For a PR, post the report and the receipt as a PR comment once the run is done: `gh pr comment <n> --body-file "$RUN/pr-comment.md"`, where the file starts with `prove-learnharness: <VERDICT> for <full head SHA>`, then the report block, then `receipt.md` in a collapsed `<details>` block. No screenshots, no secrets, no absolute home paths. A PR may auto-merge only when the latest such comment names the PR's current head SHA and says PROVED; a new push needs a new run.

## If it is BROKEN

Send the findings back to the agent that made the change: the failing steps, the answer key each was compared with, and the evidence. It fixes the app, never the answer key or the check. It may add cases and fix this skill's scripts when they are wrong, and says so in its reply. Then run the proof again on the same flows, in a fresh sub-agent again if you can. Stop after 3 rounds and report what is still BROKEN to the user, with the receipt from every round. BLOCKED is not a fix-loop case: report it.

## Limits

- Target: only instances this run started (pid files under `$RUN`). Never drive or stop the user's own server on 127.0.0.1:3774, `learnharness.service`, `~/.learnharness`, `~/.config/LearnHarness` or `~/.local/bin/lh`. If a login is missing or expired, stop and report BLOCKED. Never type or ask for a password.
- Everything a run creates (sessions, files, units) is named with the prefix `zz-prove-it` (systemd units: `lh-prove-`) so it can be found and removed. Before starting, `new-run.sh` reports live leftovers; don't silently reuse or delete them.
- Never: publish a release, push tags, touch the `nightly` release or `latest.json` on GitHub, enable Tailscale Serve or Funnel, or run `loginctl enable-linger`.
- Secrets: the fake model needs none. The real model uses your claude CLI login. Never write a secret value into this skill, a receipt or a PR comment.

## Clean up

`scripts/stop.sh "$RUN"`: refuses anything but a run folder made by `new-run.sh`; stops only what this run started (by pid file and process group, never by name, and only processes whose command line or environment names this run), removes its `lh-prove-<hash>` unit and throwaway homes, data, browser profiles and tier B archives. Evidence in `.prove-it/runs/` stays. Base builds stay cached in `$PROVE_CACHE` (newest `BASE_CACHE_KEEP` kept).

## Failures that aren't the change

A failing step is evidence, and the verdict rules above still hold. Before you write BROKEN, sort each failure into one of these, and put its class in the step line so the builder knows what to fix:

- **The change**: head fails, and base passes or the step is new. BROKEN, back to the builder.
- **Main's own bug**: base fails the same way on the same input (`compare.mjs` shows both values). BROKEN, sent back like any BROKEN, with the step labelled "base fails the same: main's bug, not this diff". The fix for the builder is to update the branch from main when main has a fix, then you run again; name that commit. Without one, it goes to the user with both values. Example: the question page's CLS scored 0.096 to 0.29 on main's identical code before 5a3910c4 (#282), so a branch whose merge base is older fails it until it is updated.
- **The environment or a tool**: the emulator, the device tool, Xvfb, the keyring, a socket path, a CI runner. BLOCKED for that step with the raw error, never BROKEN. Gotchas below and the [mobile beta](references/features/mobile-beta.md) health gate list the known ones with their working fixes.
- **A test harness that fails on both revisions before it drives anything** (a repo `scripts/smoke-*.mjs` crash, a fixture that can't start). BLOCKED for that check. Report the harness as a product bug, and prove the flow it covers another way if you can.
- **Another job holding a shared resource** (the emulator, a build slot, a port). Wait, or BLOCKED. Never take it over.

## Gotchas

- Never put `PROVE_CACHE`, a scratch clone or a base worktree inside another checkout. `next build` then takes the outer folder's lockfile as its root, writes a nested `.next/standalone`, and `build-server.mjs` can't find its entry. Make each clone its own folder on disk with plain `mktemp -d` (the shell profile points `TMPDIR` at `~/.cache/tmp`). Not under `/tmp` itself: it is a RAM-backed tmpfs, and a few clones and builds there eat the memory the builds need.
- A deep `TMPDIR` makes Unix socket paths too long (over about 107 bytes): the `tsx` CLI fails with `listen EINVAL ... tsx-<uid>/<pid>.pipe`, and Chromium's profile socket fails the same way. Run TypeScript with `node --import tsx` instead of the `tsx` CLI, and give Chromium or an AppImage a short `TMPDIR` (`mktemp -d /tmp/lh.XXXX`).
- Run the repo's own test suites in a clean environment with a throwaway HOME, never with `LH_IGNORE_ENV_KEYS=1`: it also hides the synthetic keys the tests set for themselves.
- A server started outside `lh` and the desktop app prints a one-time pairing link (`/pair#token=...`) to stdout. `start.sh` blanks the token in `app.log`. Any other server you start yourself writes a live one: grep its log for what you need instead of printing it whole, and redact it in evidence.
- Built-in plugins start disabled: enable Flashcards or Coding questions through the plugin settings endpoint before driving them.
- A proxy in front of an instance (HTTPS, fault injection) must keep the session cookie's name, `lh_session_<APP_PORT>` with the backend's port, not the proxy's.
- Electron under Xvfb: the native menu bar doesn't open with Alt or F10. Invoke the menu item's handler through the main process inspector, and put "native keyboard entry to the menu" under Not covered. Native dialogs driven with `xdotool` need a window manager (Openbox, with its theme path set) and `XAUTHORITY` for the same display. Pairing a remote server needs a Secret Service: a private D-Bus session with `gnome-keyring` and an unlocked throwaway collection. Packages for these go in the run folder (`apt-get download`, `dpkg -x`), never system-wide.
- `next build` stops once per project folder with a "SecurityFatalError" upgrade notice and says to retry; `build.sh` retries once and the notice stays in `build-*.log`. Put it under Not covered until the user decides on the upgrade.
- `next build` rewrites the tracked `next-env.d.ts`; `build.sh` restores the builder's copy.
- A `data/` folder in the worktree root (left by local test or dev runs; gitignored) is traced into `.next/standalone` and `scripts/build-server.mjs` then refuses the head build ("standalone contains a data/ directory"). That is the environment, not the change: move it into the run folder for the build and put it back afterwards (the tree hash ignores it, so the head build is still reused), and record it under Retries and fixes.
- The standalone server forks `next-server`: killing only the parent pid orphans it. Everything starts under `setsid` and stops by group.
- `/api/events` keeps a stream open, so `networkidle` never fires: wait for selectors.
- Electron downloads its binary on first use; the downloaded `chrome-sandbox` isn't SUID root here, hence `--no-sandbox`.
- A fresh Chrome profile's first load reads a different CLS (cold caches); `web-teach.mjs` loads `/chat/new` once before measuring. The reloaded session page flickers between two CLS states on identical code, so it is loaded 3 times per side and judged by its median (`CLS_MODE=absolute`: head median < 0.1; `relative`: head median vs base max, `budgets.json` `cls.relativeRule`). A CLS failure is a result, not a reason to rerun; never change `relativeNoise` or the rule yourself.
- `CLS_MODE=absolute` since the sidebar's first-load shift was fixed (it scored about 0.27 before). `compare.mjs` reads the default from `knobs.env`; a real `CLS_MODE` env var wins.
- Selfhost tier B runs under your real systemd user manager and real HOME (the unit has its own LH_HOME, port, bin dir and data); it never sets linger or Tailscale. Because the launchers under test choose where they write, `selfhost-b.sh` first asks both (base and head) for their home, unit name, shim and unit file and refuses to install unless all are the run's, and it fingerprints your real unit, shim, state file and service pid before and after.
- Don't change the worktree while a run is going: a head rebuild replaces `.next/standalone` under every running head server. Parallel checkers in one worktree are fine (each in its own run folder), because `build.sh` reuses the head build while the tree is unchanged.
- Base builds in `$PROVE_CACHE` are shared by every run and worktree: `start.sh` (base side) and `selfhost-*.sh` hold `<sha>.inuse` shared, and `build.sh` never prunes a build in use.
